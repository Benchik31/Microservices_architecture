# 5 Архитектурные решения

| ADR | Решение | Основной компромисс |
|---|---|---|
| [0001 Границы сервисов и владение данными](adr/0001-contexts-and-data.md) | Три сервиса со своими базами | Сервисы узнают об изменениях через сообщения, поэтому обновления видны с задержкой |
| [0002 Координация производственного процесса](adr/0002-orchestrated-saga.md) | Сага с сохранением состояния в сервисе «Сборка» | Центральный координатор упрощает восстановление, но его состояние и переходы становятся критичными |
| [0003 Доставка сообщений и однократный эффект](adr/0003-outbox-inbox.md) | Журналы исходящих и обработанных сообщений, ограничения уникальности | Приложения хранят дополнительные записи и должны уметь обрабатывать повторы |
| [0004 Неопределённый результат внешней операции](adr/0004-external-outcomes.md) | Записываем запрос перед отправкой и сверяем результат по исходному идентификатору | Пока результат неизвестен, материалы остаются в резерве |
| [0005 Контракты и доступ](adr/0005-contracts-and-access.md) | REST для пользовательских действий, события для процесса, проверяемые роли и версии | Клиент должен учитывать отложенный результат и конфликты ревизий |

## Как решения работают вместе

Если учётная система приняла выпуск, но ответ потерялся, «Складской учёт» сверяет исходную операцию. Он проводит расход и выпуск в своей базе, сохраняет исходящее событие, а «Сборка» после получения события завершает заказ. По HTTP пользователь видит состояние заказа и может запустить сверку. [Главный процесс](04-main-process.md), [контракты](03-contracts.md).
