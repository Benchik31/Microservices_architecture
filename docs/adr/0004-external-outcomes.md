# ADR 0004 Неопределённый результат внешней операции

- **Дата:** 2026-11-09
- **Статус:** принято для учебного проекта
- **Связанные артефакты:** [контракты](../03-contracts.md), [главный процесс](../04-main-process.md)

## Контекст

Внешняя система может сохранить операцию, а ответ потеряется по дороге. Если после таймаута отправить новый запрос на выдачу кодов, система может выпустить вторую партию. Если принять таймаут за успех, сборка или учёт начнутся без подтверждённых данных.

Во второй части эти сбои будем воспроизводить на стенде с имитаторами и учебными данными.

## Рассмотренные варианты

1. **Автоматически повторять любой POST после таймаута.** Быстро восстанавливает некоторые временные сбои, но не различает отсутствие операции и потерянный ответ успешной операции.
2. **Всегда требовать ручное подтверждение после сбоя.** Безопаснее слепого повтора, но лишает систему автоматической сверки даже при однозначном внешнем результате.
3. **Сохранять намерение, использовать постоянный идентификатор и сверять исходную операцию.** При неопределённом результате блокировать повтор эффекта; ручное вмешательство оставлять для неразрешимой неоднозначности.

## Решение

«Сборка» создаёт и сохраняет постоянные `allocationId`, `formationId` и `postingId` при первом планировании соответствующего шага. Повторная доставка команды, перезапуск и сверка не изменяют эти идентификаторы.

Перед отправкой запроса сервис сохраняет идентификатор операции, её вид, точное тело или неизменяемый снимок, хеш, время и состояние попытки. Отдельный фоновый обработчик делает вызов без открытой длительной транзакции. «Маркировка» таким способом запрашивает коды и подтверждение формирования. «Складской учёт» отражает производство во внешней системе.

| Результат | Решение сервиса |
|---|---|
| Внешняя система однозначно подтвердила операцию, идентификатор и состав совпадают | Выполнить свежую проверку результата, сохранить подтверждение и продолжить процесс |
| Получен окончательный отказ до эффекта | Передать соответствующий отказ; компенсация допустима только в пределах ADR-0002 |
| Таймаут, обрыв соединения, ответ не позволяет установить эффект | Сохранить `UNCERTAIN`, блокировать новую логическую операцию и прочитать исходную по `operationId` |
| Чтение вернуло `PROCESSING` или `UNKNOWN` | Продолжить ограниченные по частоте чтения без нового POST |
| Чтение симулятора вернуло `NOT_FOUND` | Повторить исходный POST с теми же `operationId`, `kind`, `payloadHash` и байтами тела. Имитатор гарантирует однократный эффект, даже если предыдущий запрос ещё выполняется |
| Идентификатор найден, но хеш или состав противоречат исходному | Заблокировать процесс и передать на разбор оператору |

Фоновый обработчик сверяет исходный `operationId` и увеличивает интервал между повторными запросами. После перезапуска он перечитывает незавершённые операции из базы. REST-команда оператора `reconciliation` запускает тот же алгоритм, включая точный повтор исходного POST при `NOT_FOUND` в пределах гарантии симулятора. Она не разрешает новую эмиссию, новую проводку или смену идентификатора. Окончательный `REJECTED` является терминальным результатом внешней операции: последующие чтения могут подтвердить отказ, но не изменить его на `CONFIRMED`. Для `ACCOUNTING_BLOCKED` ручной разбор и корректирующая бизнес-операция находятся за пределами учебной версии; автоматическое исправление и повтор отклонённой операции не предусмотрены.

На стенде работают два имитатора внешних систем.

- имитатор маркировки представляет границу СУЗ/ЧЗ для `allocate_codes` и `form_sets`;
- имитатор учётной системы представляет отражение производства для `post_production`.

Оба имитатора проверяют уникальность `operationId` и соответствие `kind + payloadHash`. Запрос с прежним идентификатором и тем же содержимым возвращает исходную операцию. Изменение вида или содержимого приводит к конфликту. Клиент сохраняет и при разрешённом повторе отправляет те же байты тела. Проверка уникальности и фиксация эффекта симулятора связаны атомарно: два одновременных одинаковых запроса не создают два результата. Поэтому `NOT_FOUND` позволяет безопасно повторить исходный POST, даже если чтение пересеклось по времени с ещё выполняющимся первым запросом. Это также восстанавливает падение клиента после сохранения намерения, но до первой сетевой отправки.

Режимы `DROP_RESPONSE_AFTER_COMMIT`, `REJECT_BEFORE_COMMIT`, `TEMPORARY_UNAVAILABLE` позволяют воспроизводить отказы. Режимы доступны только на стенде. Перед подключением реального API нужно проверить его гарантии идемпотентности и определить порядок восстановления.

После подтверждения формирования «Складской учёт» выполняет учёт с тем же `postingId`. Если учётная система уже создала документ, но сервис «Складской учёт» остановился до своей транзакции, после восстановления выполняется чтение исходного документа и проверка состава. Затем одна локальная транзакция фиксирует расход, выпуск, потребление резерва и `ProductionRecorded`. Уникальные ограничения не допускают второго движения. До этого момента компоненты остаются зарезервированными, готовая продукция не объявляется доступной локально. Команда освобождения допускается только для `ACTIVE`-резерва без сохранённого намерения учётной операции; наличие намерения, даже без известного внешнего результата, запрещает освобождение.

## Последствия

- Неизвестный результат маркировки переводит заказ в `RECONCILIATION_REQUIRED`. При неизвестном результате учёта проводка остаётся в ожидании сверки.
- Сбой после внешнего успеха восстанавливается чтением и завершением исходной операции. Сбой до сетевой отправки восстанавливается чтением и точным повтором при `NOT_FOUND` по гарантии симулятора. Уже подтверждённая маркировка не запускается повторно из-за недоступности учётной системы.
- При недоступности внешней системы чтения откладываются; резервы, исходные документы и привязки кодов сохраняются. Таймер не освобождает их автоматически.
- Окончательный отказ формирования после физической сборки приводит к карантину, а окончательный отказ учёта — к `ACCOUNTING_BLOCKED`. Их нельзя бесконечно считать временным сетевым сбоем.
- Если сведения внешней системы противоречат сохранённому запросу, оператор разбирает заказ, а резерв остаётся на месте.
- Для юридического аннулирования, возвратов и расформирования потребуются отдельные процессы за пределами учебной версии.
