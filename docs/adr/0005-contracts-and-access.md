# ADR 0005 Контракты взаимодействия и доступ

- **Дата:** 2026-11-09
- **Статус:** принято для учебного проекта
- **Связанные артефакты:** [контракты](../03-contracts.md), [карта контекстов](../01-context-map.md)

## Контекст

Сотруднику нужно сразу узнать, приняла ли система скан или команду. Маркировка и учёт могут ответить позже, поэтому запрос пользователя завершается после локального сохранения действия.

Одновременно повтор скана, повторная отправка формы и работа двух вкладок не должны создавать новый эффект или незаметно заменять состав. Сборщик подтверждает физическую сборку, согласующий утверждает документ. Роль проверяется в сервисе при каждом таком действии.

## Рассмотренные варианты

1. **Весь процесс через синхронные HTTP-вызовы.** Простой прототип. С каждым этапом растёт число зависимостей, а для восстановления всё равно нужно сохранять промежуточное состояние.
2. **Все действия через брокер, включая пользовательские запросы.** Единый транспорт, но сложнее интерактивная проверка ввода, авторизация и получение результата конкретного действия.
3. **REST на пользовательской границе, команды и события для межсервисного процесса.** Сохраняет быстрые локальные ответы и независимое продвижение длительной операции.

## Решение

HTTP-интерфейсы трёх сервисов и имитаторов описаны в OpenAPI 3.1.1, сообщения процесса — в AsyncAPI 3.0.0. [Контракты](../03-contracts.md).

Контракт внешних симуляторов отдельно гарантирует атомарную идемпотентность по `operationId` с проверкой `kind` и `payloadHash`. После неопределённого результата владелец интеграции сначала делает GET исходной операции. Ответ `NOT_FOUND` разрешает точный повтор исходного POST с прежними идентификатором, видом, хешем и байтами тела; `PROCESSING` и `UNKNOWN` оставляют только опрос, а окончательный `REJECTED` запрещает повтор отклонённой операции. Команда оператора `reconciliation` использует тот же алгоритм без создания нового бизнес-действия. Эта гарантия действует только для учебных симуляторов и не объявляется свойством реальных API.

Веб-интерфейс обращается к маршрутам `/api/assembly`, `/api/inventory`, `/api/marking`. Обратный прокси направляет запросы по этим путям. «Сборка» передаёт `ReserveComponents`, `AllocateSetCodes`, `FormSets`, `CommitProduction` и `ReleaseComponents` через брокер, а владельцы данных публикуют результаты. HTTP используется для действий пользователя и просмотра состояния. К внешним системам обращаются адаптеры «Маркировки» и «Складского учёта».

Запросы пользователя на изменение данных требуют `Idempotency-Key`. Для изменения существующего ресурса клиент передаёт также `If-Match` с текущей ревизией. Сервер проверяет запрос в следующем порядке.

1. Проверяет подлинность пользователя и право на действие.
2. Проверяет сохранённую идемпотентную операцию в области действия ключа. Для того же ключа, маршрута, пользователя и тела возвращает исходный ответ **до проверки устаревшей ревизии**. Повтор ключа с другим содержимым даёт `409`.
3. Для нового действия проверяет `If-Match`, бизнес-состояние и данные. Несовпадение ревизии даёт `412`.
4. Сохраняет изменение, ответ для повторного запроса и нужные исходящие сообщения одной транзакцией. Возвращает новую ревизию в `ETag`.

`202` означает, что сервис принял действие и сохранил его для обработки. Текущее состояние доступно по GET. Партия готова при `COMPLETED`. Если клиент пришлёт то же действие с новым ключом, от дублей защитят ограничения уникальности кодов и движений.

Единая служебная часть сообщения содержит `messageId`, `type`, `schemaVersion`, `occurredAt`, `correlationId`, `causationId`, `producer`, `aggregateId`, `aggregateVersion`, `data`. `correlationId` совпадает с `orderId`. Повторы публикации сохраняют `messageId`, а бизнес-идентификаторы шага сохраняются при любой доставке. Маршрут сообщения имеет вид `sets.<Type>.v1`.

Изменения контрактов проходят следующие правила:

- схемы закрыты через `additionalProperties: false`: неизвестные поля не принимаются, даже если отправитель считает их необязательными;
- добавление, удаление или изменение поля требует новой версии контракта и согласованного перехода производителей и потребителей; добавление необязательного поля внутри существующей закрытой версии не считается совместимым;
- расширение внутри прежней версии допускается только через заранее определённый в её схеме объект расширений с установленными правилами; наличие такого объекта нельзя подразумевать, если его нет в контракте;
- новая версия сообщения получает новый маршрут и схему, период совместимости и отдельное решение о миграции; неизвестная версия или тип сообщения не выполняются «по похожей схеме»;
- изменение контракта сопровождается обновлением диаграмм и примеров. Схемы и ссылки проверяются автоматически инструментами первой части.

Для учебного стенда выбран JWT с локальным тестовым издателем токенов, ограниченным сроком действия и ролями `planner`, `warehouse`, `signer`, `operator`. Сервисы проверяют подпись, издателя, получателя токена и права самостоятельно; сведения о пользователе берутся из проверенного токена, а не из свободного поля тела запроса. Планировщик создаёт задания. Сборщик сохраняет состав и подтверждает физическую сборку. Согласующий утверждает неизменяемый документ. Оператор запускает сверку. Точная матрица чтения и действий закреплена в контрактах.

На стенде роль `signer` даёт право согласовать учебный документ. Сервис сохраняет `actorId`, время и `compositionHash`, после чего фиксирует состав. Для вычисления хеша сервис сортирует единицы по `unitId`, а коды компонентов лексикографически. Затем приводит `composition` к форме JCS по RFC 8785 и применяет SHA-256. Секреты и токены не помещаются в сообщения брокера или логи. Коды в демонстрации синтетические.

## Последствия

- Пользовательская операция не ждёт всего внешнего процесса. Интерфейс показывает ожидание, необходимость сверки и блокировку.
- Контракт даёт команде возможность реализовывать три сервиса независимо и проверять совместимость до общей интеграции.
- Клиент сохраняет ключ действия для сетевого повтора и обрабатывает конфликт ревизии.
- Если база сервиса не позволила сохранить действие и результат идемпотентности, успешное принятие не подтверждается. При потерянном HTTP-ответе клиент повторяет тот же запрос с тем же ключом.
- JWT-роли и брокерные учётные записи — разные уровни доступа. У сервисов отдельные учётные записи RabbitMQ с правами только на нужные очереди и публикации; произвольная отправка события от имени другого производителя не разрешается.
- Локальная тестовая утилита выдачи токенов упрощает демонстрацию и не заявляется средством входа в рабочую систему. Реальная УКЭП, полноценное управление сотрудниками и подключение рабочих API потребовали бы отдельного проектирования.
