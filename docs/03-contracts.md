## Синхронные обращения

Интерфейс по HTTP передаёт действия сотрудников и показывает состояние операций. Запросы на резерв, выдачу кодов и списание компонентов сервисы отправляют друг другу только через RabbitMQ. Там же они публикуют результаты.

На стенде интерфейс обращается к `http://localhost:8080`. Обратный прокси-сервер передаёт запрос тому сервису, который обслуживает этот маршрут.

В контрактах `planner` обозначает планировщика, `warehouse` — сборщика, `signer` — сотрудника, подтверждающего состав, а `operator` — оператора сверки.

| Метод и путь | Владелец | Роль | Результат |
|---|---|---|---|
| `POST /api/assembly/orders` | Сборка | `planner` | `202`, задание в состоянии `RESERVING` и заголовки `Location` и `ETag`. Команда резерва может ещё ждать отправки |
| `GET /api/assembly/orders/{orderId}` | Сборка | Любая из четырёх | Ход задания, состав, ревизия и доступные подтверждения |
| `POST /api/assembly/orders/{orderId}/units` | Сборка | `warehouse` | Сохраняет КИН и коды двух компонентов одной транзакцией в состоянии `ASSEMBLING` |
| `POST /api/assembly/orders/{orderId}/physical-confirmation` | Сборка | `warehouse` | Подтверждение физической сборки всех N наборов, состояние `AWAITING_APPROVAL` и хеш `compositionHash` |
| `POST /api/assembly/orders/{orderId}/formation-approval` | Сборка | `signer` | `202`, зафиксированный состав и команда `FormSets` в таблице исходящих сообщений |
| `GET /api/inventory/stock?sku=COMP-001` | Складской учёт | Любая из четырёх | Поля `onHand`, `reserved`, `available` и ревизия. Также допускается `SET-001` |
| `GET /api/inventory/reservations/{reservationId}` | Складской учёт | Любая из четырёх | Состояние резерва |
| `GET /api/inventory/postings/{postingId}` | Складской учёт | Любая из четырёх | Состояние учётной операции и идентификатор проверенного внешнего документа |
| `POST /api/inventory/postings/{postingId}/reconciliation` | Складской учёт | `operator` | `202`, назначена сверка исходной операции с прежним `postingId` |
| `GET /api/marking/allocations/{allocationId}` | Маркировка | `warehouse`, `signer`, `operator` | Выданные учебные КИН либо состояние ожидания |
| `GET /api/marking/formations/{formationId}` | Маркировка | Любая из четырёх | Состояние формирования и подтверждённый внешний документ |
| `POST /api/marking/operations/{operationId}/reconciliation` | Маркировка | `operator` | `202`, назначена сверка по исходному `allocationId` или `formationId` |

По рецепту `recipe-demo-v1` на складе `warehouse-demo` из `2N` компонентов `COMP-001` собирают `N` наборов `SET-001`. За одно задание можно собрать от 1 до 50 наборов. Артикулы, GTIN и нормы расхода сервер берёт из рецепта. В записи каждого набора есть `unitId`, `setCodeId`, `kin` и ровно два разных кода в `componentCis`.

Сервис возвращает `202` после фиксации локальной транзакции. Если RabbitMQ недоступен, сохранённая команда ждёт отправки в таблице исходящих сообщений. Задание переходит в `COMPLETED` после подтверждения физической сборки, подтверждения формирования с тем же составом и получения события `ProductionRecorded`.

## Повторы HTTP-запросов и одновременное редактирование

Для команд `POST` обязателен заголовок `Idempotency-Key` в формате UUID. При изменении существующего ресурса клиент также передаёт `If-Match: "7"` со значением сильного `ETag` из последнего ответа `GET`. При создании задания `If-Match` не требуется. Для сверки клиент берёт `ETag` из ответа `GET` по проверяемой операции `Posting`, `Allocation` или `Formation`.

Сервис обрабатывает запрос по шагам.

1. Проверяет JWT и права пользователя, в том числе при повторном запросе.
2. Ищет ключ в собственной таблице `http_idempotency`. Отпечаток запроса включает HTTP-метод, полный нормализованный маршрут, `sub` пользователя и каноническое тело JSON. Заголовки `If-Match` и `X-Request-Id` в отпечаток не входят.
3. При совпадении ключа и отпечатка возвращает исходный статус, тело и заголовки **до проверки ревизии**. Тот же ключ с другим телом, маршрутом или пользователем даёт `409 IDEMPOTENCY_CONFLICT`.
4. Для новой команды проверяет `If-Match`, состояние и ограничения предметной области. Изменение ресурса, сохранение ответа и добавление исходящего сообщения проходят в одной локальной транзакции. Уникальный ключ и блокировка строки не дают выполнить команду дважды, если её копии пришли одновременно.

При потере HTTP-ответа клиент повторяет запрос с прежним ключом. Для нового действия клиент создаёт новый ключ и перечитывает `ETag`. Ограничение уникальности в БД разрешает закрепить КИ только за одним набором. Уникальность пары `orderId + movementType` защищает от повторной проводки. В первой версии идентификаторы заданий, результаты проводок, закрепления кодов и записи таблицы входящих сообщений сохраняются без автоматического удаления.

Заголовок `X-Request-Id` связывает записи об одном запросе. Сервер создаёт UUID, если клиент его не передал. Поле `actorId` в подтверждении состава берётся из JWT `sub`, а время `approvedAt` выставляет сервер. На стенде сотрудник подтверждает учебный состав без УКЭП.

| Код HTTP | Значение для клиента |
|---|---|
| `400` | Неверный JSON, UUID или формат заголовка |
| `401` / `403` | Нет действительного JWT или нужной роли |
| `404` | Ресурс отсутствует у сервиса. Результат внешней записи выясняется отдельно |
| `409` | Конфликт ключа, уникального кода, зафиксированного состава или текущего состояния |
| `412` | Устаревший `If-Match`. Нужно перечитать ресурс |
| `422` | Запрос соответствует формату, но нарушает правило предметной области |
| `428` | Не передан обязательный `If-Match` |
| `503` | Сервис или его собственная БД временно недоступны |

Ошибка возвращается в формате `application/problem+json` с полями `type`, `title`, `status`, `detail`, `code`, `requestId`. Сервис исключает из текста ошибки секреты, подписи и полные коды реальной маркировки. Тестовый модуль авторизации выдаёт JWT для стенда. Сервис проверяет подпись, `iss`, `aud`, `exp`, роль и `sub`. Пароли и ключи хранятся за пределами YAML и репозитория.

## Неизменяемый состав и хеш

После подтверждения физической сборки сервис «Сборка» фиксирует объект `composition = {orderId, allocationId, units}`. Сервис сортирует записи наборов по `unitId`, а внутри каждой записи — коды в `componentCis`. В обоих случаях порядок лексикографический. Поля `unitId` и `setCodeId` содержат UUID в нижнем регистре. Учебные КИ и КИН передаются в каноническом формате `^[A-Z0-9-]{8,80}$` без пробелов и управляющих символов. Перед проверкой удаляется только завершающий перевод строки от сканера.

Хеш вычисляется по формуле `compositionHash = lowercaseHex(SHA-256(UTF8(JCS(composition))))`. Сначала сервис нормализует данные и сортирует массивы, поскольку JCS сохраняет их порядок. Время подтверждения, состояние и идентификатор внешнего документа в хеш состава не входят. Сервис «Маркировка» пересчитывает хеш, проверяет, что каждый КИН входит в выдачу по этому заданию, и отправляет документ имитатору только при совпадении. Подтверждение формирования и учёт выпуска относятся к одному хешу. Сервисы отдельно проверяют количество, уникальность, права и связи. [RFC 8785](https://www.rfc-editor.org/rfc/rfc8785).

Для одного набора приведён хеш `42378cf420d468ea651c0536a05ff89f15fcb75bf42e9499b8884e942ef4a5ca`. Все коды в примере учебные. В команде `FormSets` поля `composition.orderId`, `data.orderId` и `correlationId` совпадают. [Примеры сообщений](contracts/examples.yaml).

## Каталог сообщений

В RabbitMQ используется общий обменник `sets.v1` типа `topic`. Ключ маршрутизации имеет вид `sets.<Type>.v1`. Регистр букв значим. Сервис «Сборка» публикует пять типов команд. Одиннадцать типов событий отражают результаты, которые зафиксировали складской учёт или маркировка.

| Тип сообщения | Вид | Публикует → получает | Ключевые данные |
|---|---|---|---|
| `ReserveComponents` | Команда | Сборка → Складской учёт | `orderId`, `reservationId`, `warehouseId`, `requirements` |
| `ComponentsReserved` | Событие | Складской учёт → Сборка | `orderId`, `reservationId` |
| `ComponentsReservationRejected` | Событие | Складской учёт → Сборка | Те же идентификаторы и причина нехватки или некорректной потребности |
| `AllocateSetCodes` | Команда | Сборка → Маркировка | `orderId`, `allocationId`, `setGtin`, `quantity` |
| `SetCodesAllocated` | Событие | Маркировка → Сборка | Те же идентификаторы и список пар `setCodeId` и `kin` |
| `SetCodeAllocationRejected` | Событие | Маркировка → Сборка | Те же идентификаторы и окончательный отказ без выдачи кодов |
| `ReleaseComponents` | Команда | Сборка → Складской учёт | `orderId`, `reservationId`, `CODE_ALLOCATION_REJECTED` |
| `ComponentsReleased` | Событие | Складской учёт → Сборка | Те же идентификаторы и причина компенсации |
| `FormSets` | Команда | Сборка → Маркировка | `formationId`, `reservationId`, `composition`, `compositionHash`, `approval` |
| `SetsFormationConfirmed` | Событие | Маркировка → Сборка | `formationId`, `compositionHash`, `externalDocumentId` |
| `SetsFormationRejected` | Событие | Маркировка → Сборка | `formationId` и окончательная причина отказа |
| `MarkingOperationUncertain` | Событие | Маркировка → Сборка | Исходный `operationId`, этап `ALLOCATION` или `FORMATION` и причина неизвестного результата |
| `CommitProduction` | Команда | Сборка → Складской учёт | `postingId`, резерв, подтверждение маркировки, потребность и выпуск |
| `ProductionRecorded` | Событие | Складской учёт → Сборка | `postingId` и проверенный `erpDocumentId` |
| `ProductionUncertain` | Событие | Складской учёт → Сборка | Исходный `postingId` и причина неизвестного результата |
| `ProductionBlocked` | Событие | Складской учёт → Сборка | Исходный `postingId` и окончательная ошибка учёта |

Содержимое каждого сообщения задано в `messages.yaml`. Часть проверок выполняет сам сервис. Он сверяет количество КИН и наборов (`N`), число различных компонентов (`2N`), равенство `correlationId == data.orderId`, соответствие `requirements` сохранённому рецепту и резерву, совпадение `compositionHash` и допустимость перехода состояния.

### Служебные поля и постоянные идентификаторы

| Поле | Правило |
|---|---|
| `messageId` | UUID сообщения в таблице исходящих сообщений. При повторной публикации UUID сохраняется |
| `type`, `schemaVersion` | Тип из каталога и версия `1`. Они согласованы с ключом маршрутизации |
| `occurredAt` | Время фиксации сообщения в UTC по RFC 3339 |
| `correlationId` | Значение `orderId` для всей цепочки задания |
| `causationId` | Идентификатор вызвавшего сообщения или заголовок HTTP `X-Request-Id` |
| `producer` | Значение `assembly`, `inventory` или `marking`, которое сверяется с маршрутом и правами брокера |
| `aggregateId`, `aggregateVersion` | Агрегат и версия отправителя. Для команды это состояние цепочки задания в сервисе «Сборка» |
| `data` | Содержимое конкретной команды или события, заданное схемой |

Порядок обработки определяется состоянием задания. Каждый сервис ведёт собственные версии агрегатов. По ним и отметкам времени нельзя определить общий порядок обработки. Получатель последовательно изменяет свой агрегат и сверяет ожидаемый шаг. Позднее сообщение не возвращает завершённый шаг в предыдущее состояние. Сообщение о будущем шаге сохраняется для последующей проверки или разбора.

Сервис «Сборка» создаёт `reservationId`, `allocationId`, `formationId` и `postingId` один раз при планировании соответствующего шага и сохраняет их до публикации. При повторной доставке эти идентификаторы, содержимое сообщения и внешний `operationId` остаются прежними. Получатель выявляет повтор доставки по `messageId`. Постоянный идентификатор операции защищает от повторного расхода, даже если у дубликата новый `messageId`.

### Очереди и доставка

После перезапуска RabbitMQ сохраняет очереди сервисов `assembly.v1`, `inventory.v1` и `marking.v1`. Каждая привязана к ключам входящих сообщений из соответствующего AsyncAPI. Команда `ReserveComponents` попадает в `inventory.v1`, событие `ComponentsReserved` — в `assembly.v1`. Несколько экземпляров сервиса могут читать его очередь. Блокировки в БД и проверка повторов защищают данные при одновременной обработке.

Изменение данных и запись в таблицу исходящих сообщений проходят в одной транзакции. Фоновый отправитель публикует сообщения с режимом сохранения `deliveryMode=2` и признаком `mandatory`. Он помечает сообщение отправленным после подтверждения публикации, если брокер не вернул сообщение как немаршрутизируемое. Если ответ брокера потерян, отправитель публикует то же сообщение ещё раз.

Получатель одной локальной транзакцией добавляет запись в таблицу входящих сообщений, изменяет свой агрегат и сохраняет новые исходящие сообщения. После фиксации транзакции он отправляет брокеру подтверждение обработки. При сбое между этими шагами брокер доставляет сообщение повторно. Таблица входящих сообщений позволяет распознать уже выполненную обработку.

RabbitMQ доставляет сообщения не менее одного раза. База PostgreSQL каждого сервиса позволяет применить изменения по операции один раз. Сервис «Сборка» завершает задание после подтверждения всех обязательных шагов.

Для временных ошибок до фиксации транзакции у каждого сервиса есть очереди отложенных повторов `*.retry-5s.v1`, `*.retry-30s.v1` и `*.retry-120s.v1`. Если после трёх повторов ошибка сохраняется, сообщение попадает в очередь разбора `*.dlq.v1` и оператор получает уведомление. Если соединение оборвалось, брокер снова доставляет неподтверждённое сообщение. При ручном возврате из очереди разбора сохраняются `messageId`, идентификаторы операций и содержимое. Задание и резерв остаются в прежних состояниях. Недостаток компонентов подтверждается отдельным событием об отказе. Если результат внешней записи неизвестен, сервис сохраняет это состояние, а фоновый обработчик сверяет исходную операцию.

Команда `ReleaseComponents` действует только для резерва `ACTIVE`, если сервис ещё не сохранил намерение провести выпуск. После начала учёта поздняя команда освобождения не увеличит остаток, даже если внешняя учётная система ещё не ответила. Состояние `RELEASED` сохраняется в БД, чтобы повторная команда `ReserveComponents` не создала новый резерв.

## Внешние имитаторы и сверка

Имитатор маркировки (`localhost:8091`) принимает `allocate_codes` и `form_sets`. Имитатор учётной системы (`localhost:8092`) принимает только `post_production`. У обоих одинаковая структура HTTP-запросов и собственные данные. Сервис отправляет `POST /operations` с полями `operationId`, `kind`, `payloadHash` и `payload`, затем сверяет результат через `GET /operations/{operationId}`. До первого `POST` сервис сохраняет в своей БД исходные байты запроса, хеш, идентификатор и сведения о попытке. Повтор запроса на выдачу возвращает уже сохранённые коды.

`payloadHash = SHA-256(JCS(payload))` охватывает все данные в `payload`, а `compositionHash` — только состав набора. Имитатор проверяет хеш и атомарно связывает `operationId` с `kind`, содержимым и результатом. Повтор запроса с тем же идентификатором и содержимым возвращает исходную операцию. При том же идентификаторе и другом виде операции, хеше или содержимом имитатор возвращает `409`. Фоновый обработчик обращается к имитатору после фиксации намерения в БД. Сервис закрывает транзакцию и снимает блокировки до сетевого вызова.

| Наблюдаемый результат | Действие сервиса |
|---|---|
| `CONFIRMED` | Сверить идентификатор, вид, хеш, состав, количество и внешний результат. Завершить исходный локальный шаг |
| `PROCESSING` / `UNKNOWN` | Продолжать опрос по прежнему идентификатору и сохранять резерв, коды и исходное содержимое запроса |
| Таймаут или обрыв | Сохранить состояние `UNCERTAIN`, затем прочитать исходную операцию |
| `NOT_FOUND` | Повторить сохранённый запрос с теми же идентификатором, видом, хешем и байтами. Имитатор применит операцию один раз, даже если оба запроса дойдут |
| `REJECTED` при выдаче КИН | Освободить резерв при подтверждённом отсутствии выданных кодов |
| `REJECTED` при формировании | Перевести задание в `QUARANTINED` и сохранить резерв, поскольку физическая сборка уже подтверждена |
| `REJECTED` при учёте | Перевести задание в `ACCOUNTING_BLOCKED`, сохранить резерв и закрепления кодов для разбора |

Если сервис остановился до первого `POST`, после перезапуска он начнёт со сверки по сохранённому идентификатору. При `NOT_FOUND` отправит сохранённый запрос. Если первый запрос успел уйти и придёт позже, уникальный `operationId` защитит от второго применения. Для реальной интеграции порядок повтора определяет протокол внешней системы. Случаи, для которых протокол не даёт безопасного способа повтора, разбирает оператор.

`REJECTED` — окончательный результат имитатора. Сверка для `ACCOUNTING_BLOCKED` может подтвердить прежнюю блокировку. Сведения об окончательном отказе сохраняются для оператора. Исправление отклонённой учётной операции и физическое расформирование остаются за пределами первой версии.

Для демонстраций оператор вызывает `PUT /test/faults/{operationId}` на локальном стенде с отдельным ключом. Режим `REJECT_BEFORE_COMMIT` фиксирует окончательный отказ без применения операции. Режим `DROP_RESPONSE_AFTER_COMMIT` обрывает ответ после фиксации эффекта. В режиме `TEMPORARY_UNAVAILABLE` имитатор возвращает `503`. Оператор проверяет результат по идентификатору операции и счётчику её применений.

## Версии контрактов

Схемы используют `additionalProperties: false`. Изменение допустимых данных, включая добавление необязательного поля, требует новой версии схемы, сообщения и ключа маршрутизации `.v2`. Уточнение текста или примера не требует новой версии, пока правила приёма данных прежние.
